## 5. ANIMATION REQUIREMENTS (this is the priority — be specific and ambitious here)

This is the most important part of the brief. Don't just fade sections in — make scrolling feel choreographed.

Use Framer Motion's scroll-linked features (`useScroll`, `useTransform`, `whileInView`) to implement:

* **Scroll-triggered reveals**: sections/elements animate in (fade + slide, scale, or clip-path reveal) as they enter the viewport, using `whileInView` with sensible `viewport={{ once: true, margin: ... }}` settings
* **Staggered children**: lists (skills, projects, timeline items) animate in one-by-one with a small delay between each, not all at once
* **Scroll-linked parallax**: at least one element (e.g., hero background shape, section headings, or an accent graphic) moves at a different speed than the scroll for depth
* **Progress-based effects**: consider a scroll progress indicator, or elements that scale/rotate/change opacity tied directly to scroll position via `useScroll`'s `scrollYProgress`
* **Smooth micro-interactions**: hover states on project cards and buttons (subtle lift, border glow, or scale — nothing garish), animated underline on nav links, smooth focus states
* **Page load sequence**: hero elements should stagger in on first load, not just appear
* **Section transitions**: as the user moves from one section to the next, consider subtle background color/theme shifts or shape transitions that make it feel like one continuous, moving canvas rather than stacked static blocks

Constraints:
* Respect `prefers-reduced-motion: reduce` — disable/simplify non-essential motion for users who request it
* Animations must not hurt performance — avoid animating expensive CSS properties, prefer `transform`/`opacity`
* Keep it tasteful: smooth easing (avoid linear), moderate durations (~0.3–0.8s for most transitions), no bouncing/gimmicky effects unless it clearly fits the brand
* Test that scrolling feels smooth on both desktop and mobile (touch scroll), not janky

## 9. CONTENT EDITING WORKFLOW (why we use data files instead of hardcoding in JSX)

Even without a database, don't scatter content inline across components. Structure it like:

```
/content
  profile.ts       // name, title, tagline, bio, social links, resume URL
  skills.ts        // typed array grouped by category
  projects.ts       // typed array of project objects
  experience.ts     // typed array
  education.ts      // typed array
  achievements.ts    // typed array
```

Components import from `/content` and render dynamically from these arrays (`.map()`), so adding a new project later means adding one object to `projects.ts`, not editing JSX. This also makes a future migration to a real CMS/database straightforward without a rewrite.
